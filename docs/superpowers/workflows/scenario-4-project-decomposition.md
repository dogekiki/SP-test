# 场景 4:大型项目分解工作流

> **适用场景**:用户请求涉及多个独立子系统,单一 spec 无法覆盖
> **触发词**:"构建一个完整的...系统,含 A、B、C、D"
> **判定信号**:请求描述 2+ 个可独立运行、独立测试的子系统

---

## 工作流总览

```
阶段 A: 全局分解
  │
  ├─ A1  using-superpowers        (入口判定)
  ├─ A2  brainstorming            (范围评估 → 标记过大 → 分解)
  ├─ A3  子项目划分与排序
  └─ A4  子项目关系图
       │
       ▼
阶段 B: 子项目循环(对每个子项目重复)
  │
  ├─ B1  brainstorming            (该子项目设计)
  ├─ B2  writing-plans            (该子项目计划)
  ├─ B3  using-git-worktrees      (隔离)
  ├─ B4  subagent-driven-development (执行)
  │      └─ 内循环: TDD / debugging / review / verification
  ├─ B5  finishing-a-development-branch (该子项目收尾)
  └─ B6  集成验证
       │
       ▼
阶段 C: 全局集成
  ├─ C1  跨子项目集成测试
  ├─ C2  verification-before-completion
  └─ C3  最终交付
```

---

## 阶段 A:全局分解

### A1. 入口判定

**Skill**: `using-superpowers`

**执行指令**:
```
判定用户请求类型:
- 若请求描述多个独立子系统(例:"含轨迹规划、避障、通信、地面站")
  → 本工作流(场景4)
- 若单一功能 → 转场景1

过程技能优先。宣告:
"使用 using-superpowers 判定:大型项目,需先分解"
```

**通过准则**:明确识别为多子系统项目

---

### A2. 头脑风暴(范围评估与分解)

**Skill**: `brainstorming`

**执行指令**:
```
执行 brainstorming,但在"探索项目上下文"后立即进行范围评估:

1. 探索项目上下文(同场景1)

2. 范围评估(关键分歧点):
   若请求描述多个独立子系统:
   - 立即标记:"此项目过大,单一 spec 无法覆盖,需先分解"
   - 不要花问题去细化整个项目的细节
   - 转入分解流程(步骤3)

3. 分解流程:
   a. 识别独立子系统:
      - 问:哪些部分可独立运行、独立测试?
      - 问:它们之间的依赖关系是什么?
   
   b. 划分子项目(与用户协作):
      - 每个子项目应能产出可工作的、可测试的软件
      - 避免过度分解(一个子项目不应只剩单文件)
   
   c. 排序:
      - 基础设施/无依赖的先
      - 依赖其他的后
      - 问:哪个子项目是其他子项目的前提?
   
   d. 绘制关系图:
      - 子项目间的依赖箭头
      - 哪些可并行,哪些必须顺序

4. 输出全局分解文档:
   保存到 docs/superpowers/specs/YYYY-MM-DD-<system>-decomposition.md
   含:子项目列表、依赖关系、建议顺序

5. 用户审核分解方案,获批后进入阶段B
```

**关键分歧**:场景4 与场景1 的区别在于步骤2——范围评估发现过大后**不细化整个项目**,而是先分解

**输出**:`docs/superpowers/specs/YYYY-MM-DD-<system>-decomposition.md`

**通过准则**:用户批准分解方案和子项目顺序

---

### A3. 子项目划分模板

**执行指令**:
```
对每个子项目,记录以下信息:

## 子项目 N: <名称>
- 职责: 一句话描述
- 依赖: 列出依赖的其他子项目(无则填"无")
- 产出: 可工作的、可测试的软件
- 建议顺序: 第 N 个执行
- 可否并行: 是/否(与哪些子项目并行)

示例:
## 子项目 1: 轨迹规划
- 职责: 生成飞行器从起点到目标的最优轨迹
- 依赖: 无
- 产出: 可独立运行的轨迹规划模块 + 单元测试
- 建议顺序: 第 1 个
- 可否并行: 否(是其他子项目的基础)

## 子项目 2: 避障
- 职责: 在轨迹规划基础上加入障碍物规避
- 依赖: 子项目 1(轨迹规划)
- 产出: 集成避障的轨迹规划模块 + 测试
- 建议顺序: 第 2 个
- 可否并行: 否
```

---

### A4. 子项目关系图

**执行指令**:
```
用 dot 语法绘制子项目依赖关系:

digraph project_decomposition {
    "子项目1: 轨迹规划" [shape=box];
    "子项目2: 避障"     [shape=box];
    "子项目3: 通信"     [shape=box];
    "子项目4: 地面站"   [shape=box];

    "子项目1: 轨迹规划" -> "子项目2: 避障";
    "子项目1: 轨迹规划" -> "子项目4: 地面站";
    "子项目3: 通信"     -> "子项目4: 地面站";

    // 并行标记
    subgraph cluster_parallel {
        label = "可并行";
        "子项目2: 避障";
        "子项目3: 通信";
    }
}

标注:
- 顺序执行: 子项目1 → (子项目2 ∥ 子项目3) → 子项目4
- ∥ 表示可并行
```

---

## 阶段 B:子项目循环

> 对分解方案中的每个子项目,重复执行 B1-B6

### B1. 子项目设计

**Skill**: `brainstorming`

**执行指令**:
```
对当前子项目走完整 brainstorming 流程(同场景1步骤1):

1. 探索项目上下文(含已完成的前序子项目)
2. 适时提供可视化伴侣
3. 逐个提问澄清(聚焦此子项目的目的、约束、成功标准)
4. 提出 2-3 种方案
5. 呈现设计(分段获批)
6. 写设计文档:
   docs/superpowers/specs/YYYY-MM-DD-<subproject>-design.md
7. 规格自审
8. 用户审核规格
9. 过渡到 writing-plans

硬门控:同场景1
```

**输出**:`docs/superpowers/specs/YYYY-MM-DD-<subproject>-design.md`

---

### B2. 子项目计划

**Skill**: `writing-plans`

**执行指令**:
```
同场景1步骤2,但额外注意:
- 标注本子项目对前序子项目的依赖
- 集成测试需包含与前序子项目的接口验证
- 保存到 docs/superpowers/plans/YYYY-MM-DD-<subproject>.md
```

**输出**:`docs/superpowers/plans/YYYY-MM-DD-<subproject>.md`

---

### B3. 工作区隔离

**Skill**: `using-git-worktrees`

**执行指令**:
```
同场景1步骤3:
- 检测现有隔离
- 优先原生工具,回退 git worktree
- 宣告:"使用 using-git-worktrees 技能设置隔离工作区"
```

---

### B4. 子项目执行

**Skill**: `subagent-driven-development`

**执行指令**:
```
同场景1步骤4,每任务派遣子代理:

内循环:
- test-driven-development(每任务)
- systematic-debugging(遇 bug)
- dispatching-parallel-agents(任务内多独立子任务)
- requesting-code-review + receiving-code-review(任务后)
- verification-before-completion(声称完成前)

连续执行,任务间不暂停
```

---

### B5. 子项目收尾

**Skill**: `finishing-a-development-branch`

**执行指令**:
```
同场景1步骤5:
- 验证测试
- 检测环境
- 呈现选项(merge/PR/cleanup)
- 执行选择
- 清理工作区
```

---

### B6. 子项目集成验证

**执行指令**:
```
子项目收尾后,额外执行集成验证:

1. 若本子项目依赖前序子项目:
   - 运行跨子项目集成测试
   - 验证接口兼容性
   - 确认未破坏前序子项目的功能

2. 更新全局进度:
   - 在分解文档中标记本子项目为"已完成"
   - 记录实际耗时、遇到的问题、经验教训
   - 保存到 docs/superpowers/specs/YYYY-MM-DD-<system>-decomposition.md

3. 判定下一个子项目:
   - 若有可并行的未完成子项目 → 可考虑 dispatching-parallel-agents
   - 否则顺序进入下一个子项目,回到 B1
```

**通过准则**:本子项目独立测试通过 + 与前序子项目集成测试通过

---

## 阶段 C:全局集成

### C1. 跨子项目集成测试

**执行指令**:
```
所有子项目完成后,执行全局集成:

1. 端到端测试:
   - 覆盖所有子项目的完整业务流程
   - 验证子系统间的数据流和控制流

2. 性能与稳定性:
   - 全系统负载测试
   - 长时间运行稳定性

3. 回归测试:
   - 确认所有子项目的单元测试仍通过
   - 无子项目间的回归

记录到 docs/superpowers/specs/YYYY-MM-DD-<system>-integration-test.md
```

---

### C2. 全局验证

**Skill**: `verification-before-completion`

**执行指令**:
```
声称"全系统完成"前,强制执行:

1. IDENTIFY: 什么命令证明全系统正常?
   - 全套单元测试
   - 端到端集成测试
   - 性能基准

2. RUN: 执行完整命令(新鲜跑,不引用历史结果)

3. CONFIRM: 确认输出(亲自看结果,不凭感觉)

4. CLAIM: 只有证据齐备才可声称完成

铁律:本条消息没跑验证命令,就不能声称通过
```

---

### C3. 最终交付

**执行指令**:
```
1. 汇总所有子项目的交付物:
   - 设计文档(specs)
   - 实现计划(plans)
   - 代码与测试
   - 集成测试报告

2. 更新项目文档:
   - README(若需要)
   - 架构说明
   - 部署指南

3. 最终 git 提交与标签

4. 向用户呈现完整交付清单
```

---

## 关键约束

| 约束 | 说明 |
|------|------|
| **先分解后细化** | 阶段A不细化整个项目,只划分子项目和顺序 |
| **独立周期** | 每个子项目有独立的 spec → plan → implementation 周期 |
| **顺序尊重** | 子项目按依赖排序,被依赖的先完成 |
| **集成验证** | 每个子项目完成后(B6)和全部完成后(C1)都要做集成测试 |
| **硬门控** | 每个子项目的 B1 未获设计批准前,B2-B6 不得开始 |
| **证据先行** | C2 全局完成前必须跑验证命令拿证据 |

---

## 用户交互点

| 阶段 | 步骤 | 交互类型 | 等待用户输入? |
|------|------|----------|---------------|
| A | A2 | 分解方案审核 | 是(等批准或调整) |
| A | A3 | 子项目顺序确认 | 是(等确认顺序) |
| B | B1 | 逐个提问 + 设计分段确认 + 规格审核 | 是(每子项目都交互) |
| B | B4 | 仅 BLOCKED 时 | 是(仅遇阻时) |
| B | B5 | 集成方式选择 | 是(每子项目收尾时) |
| B | B6 | 下一个子项目确认 | 可选(可设为自动继续) |
| C | C3 | 最终交付确认 | 是 |

---

## 与场景1的区别

| 维度 | 场景1(新功能开发) | 场景4(大型项目分解) |
|------|-------------------|---------------------|
| **范围** | 单一 spec 可覆盖 | 需多个 spec |
| **brainstorming 重点** | 细化设计 | 先分解,再对子项目细化 |
| **执行次数** | 1 次 brainstorming → 1 次 plan → 1 次执行 | N 次 brainstorming → N 次 plan → N 次执行 |
| **集成测试** | 无(单一功能) | 有(B6 子项目间 + C1 全局) |
| **并行机会** | 任务内(dispatching-parallel-agents) | 子项目间(无依赖的可并行) |

---

## 退出条件

- **正常退出**:阶段C完成,全系统通过集成测试,已交付
- **异常退出**:阶段A用户放弃分解;阶段B某子项目 BLOCKED 无法解决
- **部分退出**:可只完成部分子项目,每个已完成的子项目都是可用的独立软件
